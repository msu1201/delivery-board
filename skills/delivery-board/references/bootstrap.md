# Bootstrap an existing project

The CLI init command only creates an empty sidecar. The Agent following this procedure does the investigation and normalization. It is not a built-in scanner or a guaranteed reconstruction of the project's history.

1. Establish the intended project root and outcome. Reuse existing board records and respect other active writers. Read the current source configuration and adapter contract before writing. Keep the tool checkout separate.
2. Inspect relevant plans, specifications, task lists, handoffs, acceptance records and tests. Read local Git history for changes and revisions. Relevant remote issues, PRs or CI may be read with the user's existing authorization and available tools; lack of access is a recorded gap, not a reason to invent evidence. The viewer itself does not query these services.
3. With incomplete history, inventory present capabilities and observed implementation. Draft a current baseline instead of pretending to recover every past task. Identify sources, observations, proposed work and unresolved questions separately. Code presence is not acceptance; a commit is not proof of end-to-end completion. Test results only cover what was actually run and verified.
4. Derive tasks from supported outcomes. Present inferred module/phase structure as a proposal; do not infer chronology from folders or dependency edges from list position. Ask about current goals, priority or ambiguous scope only when the answer materially changes the graph. Save uncertain supported items as unknown; keep speculative additions in notes until adopted.
5. Put inventory provenance and unresolved questions in the sidecar WORKFLOW.md and relevant supported record fields (such as checkpoint.summary and references; consult the schema). Do not invent schema fields. Never convert confidence estimates into completion percentages. Missing milestone scope stays unknown.
6. Normalize supported task and journey records using stable IDs. Add only evidence-backed or explicitly decided dependencies. Record human acceptance and delivery only from actual decisions/evidence. A partially populated board is preferable to fabricated completeness.
7. Run the CLI check, open the board, and report what was mapped, what was proposed or remains unknown, and what the user needs to clarify. Structural validation is not factual verification. Preserve business code. Global skill installation is optional and outside ordinary setup unless requested.
8. As accepted plans evolve, follow maintenance.md in this directory during the work session. Automatic browser polling displays saved updates; it does not maintain records or inspect new conversations.

Example: a repository has a working login page and commits but no acceptance notes. Record the observed implementation and its revision, keep acceptance unknown, and ask whether login is in the current delivery scope. Do not mark it accepted or infer that it precedes checkout without supporting requirements.
